# Installation and authoring verification

This record covers the combined installation and check/remediation authoring delivery for findings I01–I10 and D01–D06. It separates implemented behavior, local evidence, and cloud evidence that still requires an authorized operator.

It does **not** claim that an immutable Scorecards release has been published or that a new GitHub installation has been proven live.

## Supported route

1. A release maintainer publishes and protects a reviewed release, and an operator verifies its full source SHA.
2. The operator follows the [Platform Installation Guide](../guides/platform-installation.md) with exclusive installation writing for the complete run. `SOURCE_SHA` identifies the immutable upstream source; `INSTALLED_MAIN_SHA` identifies the personalized commit deployed to Pages.
3. Public Pages uses unauthenticated delivery proof. Restricted Pages uses the documented browser session without sending a repository token or changing visibility.
4. A service team follows the [Service Installation Guide](../guides/service-installation.md), including the individual result, consolidation, `all-services.json`, and fresh-browser first-service gate.
5. Authors follow the [Check Development Guide](../guides/check-development-guide.md). Agents load the canonical `creating-scorecards-checks` skill and, when applicable, `creating-scorecards-remediations`.

The README and documentation indexes link into this route; they do not define competing schemas or installation procedures.

## Outstanding authorized proof

The separate `scorecards-fresh-install-proof` task owns all eight real cloud installation scenarios, including live restricted Pages. This change neither performs nor waives them.

That proof requires:

- a reviewed, protected immutable release and its full source SHA;
- disposable central and service repositories outside `scorecards-workspace`;
- least-privilege installer, catalog, and workflow credentials supplied without logging values;
- GitHub Actions and Pages availability for the selected visibility;
- an authenticated operator session for restricted Pages;
- a verified `catalog` rule that permits the intended job-scoped write; and
- exclusive installation writing for the complete installation run.

No release, repository, token, secret, Pages visibility, ruleset, dispatch,
merge, or cloud installation was created or changed. A local hash-inspection
command was accidentally invoked in update mode and pushed a timestamp-only
`catalog/current-checks.json` refresh (`107e29f`); revert `2954303` immediately
restored the prior bytes. Those two audit commits remain in `catalog` history.
